# 运行环境指标采集表

本文专门说明运行环境指标应该采集哪些字段、字段含义是什么、如何采集，以及它们理论上如何影响程序执行时间。运行环境指标不描述程序代码本身，而是描述“程序在哪个系统、什么硬件、什么线程配置、什么负载状态下运行”。

对于本项目，建议把运行环境指标和 AST/CFG/LLVM IR 静态指标分开保存。静态代码指标回答“程序长什么样”，运行环境指标回答“程序是在什么机器条件下跑出来这个时间的”。

## 1. 数据表设计

建议至少拆成两张表。

| 数据表 | 一行代表什么 | 主要用途 |
|---|---|---|
| `run_environment.csv` | 一种稳定运行环境配置 | 记录机器、系统、CPU、内存、电源、OpenMP 默认设置 |
| `run_records.csv` | 某个程序的某一轮运行 | 记录该轮运行时长、运行前后系统负载、可用内存、退出状态 |

如果只做第一版实验，也可以先把 `run_environment.csv` 的字段合并到 `environment_manifest.json` 中，但正式建模时建议表格化，方便和 `results.csv` 通过 `env_id` 关联。

## 2. 运行环境基础标识字段

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `env_id` | 运行环境编号 | 手动命名，例如 `win_openmp_4t_baseline` | 用于区分不同机器/线程/系统配置；没有它就无法判断时间差来自代码还是环境 | 必采 |
| `timestamp` | 环境采集时间 | Python `datetime` 或系统时间 | 便于追踪环境是否随时间变化，例如系统更新、驱动更新、电源策略变化 | 必采 |
| `machine_id` | 机器标识 | 手动设置或对主机名做匿名化 | 用于区分不同物理机器；同一程序在不同机器上时间不可直接混合 | 建议采 |
| `working_directory` | 实验工作目录 | Python `Path.cwd()` | 路径本身不影响运行时间，但影响输入文件位置、相对路径和复现实验 | 建议采 |
| `dataset_root` | 数据集根目录 | 手动记录或 pipeline 参数 | 确认运行的到底是 PolyBench、Rodinia OpenMP 还是其他数据源 | 必采 |

## 3. 操作系统指标

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `os_name` | 操作系统名称 | Python `platform.system()` | Windows、Linux、WSL、虚拟机的进程调度、文件系统和计时行为不同 | 必采 |
| `os_version` | 操作系统版本 | Python `platform.version()` 或 PowerShell `Get-CimInstance Win32_OperatingSystem` | 系统版本会影响调度器、库版本、线程实现和安全补丁开销 | 必采 |
| `kernel_version` | 内核版本 | Linux `uname -r`，Windows 可记录 build number | 内核调度、内存管理、OpenMP 线程调度可能随版本变化 | 建议采 |
| `system_arch` | 系统架构 | Python `platform.machine()` | x86_64、ARM64 等架构差异会直接影响指令集和性能 | 必采 |
| `python_version` | Python 版本 | `python --version` | 如果用 Python harness 计时，Python 版本可能影响调度脚本行为；对程序本体影响较小 | 建议采 |
| `shell` | 执行 shell | PowerShell、cmd、bash | shell 对环境变量设置和路径解析有影响，一般不直接影响 kernel 执行时间 | 可选 |

## 4. CPU 硬件指标

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `cpu_model` | CPU 型号 | PowerShell `Get-CimInstance Win32_Processor` | CPU 微架构、主频、cache、SIMD 能力不同，运行时间可能差异很大 | 必采 |
| `cpu_vendor` | CPU 厂商 | 系统 API 或 CPU 名称解析 | Intel、AMD、Apple、ARM 不同平台优化效果不同 | 建议采 |
| `cpu_physical_cores` | 物理核心数 | Python `psutil.cpu_count(logical=False)` | 决定 OpenMP 多线程可用的真实并行资源 | 必采 |
| `cpu_logical_cores` | 逻辑线程数 | Python `psutil.cpu_count(logical=True)` | 超线程会影响并行加速比；线程数超过物理核时可能收益下降 | 必采 |
| `cpu_base_freq_mhz` | CPU 标称基础频率 | 系统 API 或手动记录 | 主频越高，计算密集型程序通常越快，但会受睿频和功耗限制影响 | 建议采 |
| `cpu_max_freq_mhz` | CPU 最大频率 | `psutil.cpu_freq()` 或系统信息 | 睿频能力影响短程序和单线程程序运行时间 | 建议采 |
| `cpu_current_freq_mhz` | 当前频率 | `psutil.cpu_freq()`，Windows 上可能不稳定 | 动态频率变化会造成运行时间波动，是解释异常轮次的重要线索 | 可选 |
| `cpu_l1_cache_kb` | L1 cache 大小 | 手动记录或硬件查询工具 | 小数组/局部性强程序可能受 L1 影响明显 | 可选 |
| `cpu_l2_cache_kb` | L2 cache 大小 | 手动记录或硬件查询工具 | 中等工作集程序受 L2 容量和延迟影响 | 可选 |
| `cpu_l3_cache_mb` | L3 cache 大小 | 手动记录或硬件查询工具 | 多线程共享数据、图算法、矩阵块大小会受 L3 影响 | 建议采 |
| `simd_support` | SIMD 指令能力 | CPU 信息，例如 AVX2、AVX-512 | 编译器能否向量化会显著影响数值程序，如矩阵、stencil、K-means | 可选 |

## 5. 内存与存储指标

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `ram_total_gb` | 总内存 | Python `psutil.virtual_memory().total` | 数据集过大时，内存容量不足会导致分页或失败 | 必采 |
| `ram_available_gb` | 环境采集时可用内存 | Python `psutil.virtual_memory().available` | 可用内存低会增加换页风险，使运行时间变慢且波动 | 必采 |
| `memory_speed_mts` | 内存频率 | 手动记录或硬件工具 | 内存带宽密集程序，如 BFS、hotspot、srad，会受内存速度影响 | 可选 |
| `memory_channels` | 内存通道数 | 手动记录 | 双通道/单通道会影响带宽，进而影响内存密集程序 | 可选 |
| `storage_type` | 磁盘类型 | 手动记录，例如 SSD/HDD/NVMe | 如果运行时间包含输入文件读取，磁盘速度会影响端到端时间 | 建议采 |
| `storage_free_gb` | 可用磁盘空间 | 系统 API | 空间不足会影响输出文件、临时文件和编译过程 | 可选 |

## 6. 电源与系统负载指标

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `power_source` | 是否接电源 | Windows 电源 API 或手动记录 | 笔记本电池模式可能限制 CPU 频率，导致时间变长 | 建议采 |
| `power_plan` | 电源计划 | PowerShell `powercfg /GETACTIVESCHEME` | 平衡/节能/高性能模式会影响 CPU 频率策略 | 必采 |
| `battery_saver_enabled` | 是否省电模式 | Windows 设置或手动记录 | 省电模式会限制频率和后台调度，影响时间稳定性 | 建议采 |
| `cpu_percent_before` | 运行前 CPU 占用 | `psutil.cpu_percent(interval=1)` | 后台负载高会抢占 CPU，使运行时间变慢 | 必采 |
| `ram_available_before_gb` | 运行前可用内存 | `psutil.virtual_memory().available` | 可用内存不足会导致分页、cache 状态变化或分配失败 | 必采 |
| `process_count_before` | 运行前进程数量 | `len(psutil.pids())` | 进程多不一定慢，但可作为后台干扰的粗略信号 | 建议采 |
| `background_load_level` | 后台负载等级 | 根据 CPU 占用人工分为 low/medium/high | 用于标记异常实验条件；高负载样本应谨慎用于训练 | 建议采 |

## 7. OpenMP 运行指标

Rodinia OpenMP 实验必须记录这一组字段。它们对运行时间的影响可能不亚于代码本身。

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `parallel_model` | 并行模型 | 固定为 `openmp` | 用于和串行、CUDA、OpenCL 区分；不同并行模型不能直接混在一起 | 必采 |
| `omp_num_threads` | OpenMP 线程数 | 环境变量 `OMP_NUM_THREADS` | 线程数直接决定并行度；过少利用不足，过多可能调度和带宽竞争 | 必采 |
| `omp_schedule` | OpenMP 调度策略 | 环境变量 `OMP_SCHEDULE` 或程序参数 | `static`、`dynamic`、`guided` 对负载均衡和调度开销影响很大 | 必采 |
| `omp_dynamic` | 是否允许动态调节线程数 | 环境变量 `OMP_DYNAMIC` | 如果开启，实际线程数可能变化，导致样本不可复现 | 必采 |
| `omp_proc_bind` | 线程是否绑定核心 | 环境变量 `OMP_PROC_BIND` | 绑定核心可减少迁移，提高 cache 局部性和稳定性 | 建议采 |
| `omp_places` | 线程放置位置 | 环境变量 `OMP_PLACES` | 控制线程分布在 cores/threads/sockets 上，影响 NUMA 和 cache | 可选 |
| `omp_nested` | 是否允许嵌套并行 | 环境变量 `OMP_NESTED` 或运行时设置 | 嵌套并行可能导致线程过量创建和调度开销 | 可选 |
| `thread_affinity` | 线程亲和性策略 | 手动记录或系统工具 | 决定线程是否固定在特定核心上，影响稳定性 | 建议采 |

建议第一阶段固定：

```text
OMP_SCHEDULE=static
OMP_DYNAMIC=false
```

然后把 `OMP_NUM_THREADS=1,2,4,8` 作为不同实验配置分别采集。每个线程数都应有不同的 `env_id` 或至少不同的 `run_config_id`。

## 8. 每轮运行快照指标

这一组字段应该写入 `run_records.csv`，每一轮运行都记录一次。它们用于解释某些轮次为什么异常慢。

| 指标字段 | 采集对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `run_id` | 单轮运行编号 | 程序生成 | 用于唯一定位一次运行 | 必采 |
| `program_id` | 程序编号 | pipeline 生成 | 用于关联静态代码指标 | 必采 |
| `env_id` | 环境编号 | 从运行环境表继承 | 用于关联机器和线程配置 | 必采 |
| `input_id` | 输入规模编号 | 手动或 manifest 生成 | 同一程序不同输入规模运行时间不能混合 | 必采 |
| `run_index` | 第几轮正式运行 | 计数器 | 用于分析运行时间随轮次是否变化，例如 cache/warmup 效应 | 必采 |
| `timestamp_start` | 开始时间 | Python `datetime` | 用于追踪运行顺序和系统状态 | 建议采 |
| `timestamp_end` | 结束时间 | Python `datetime` | 用于核对运行耗时和日志 | 建议采 |
| `runtime_sec` | 本轮运行时间 | `time.perf_counter()` | 运行时间标签的原始值，后续 median/mean/std 都从它计算 | 必采 |
| `cpu_percent_before` | 运行前 CPU 占用 | `psutil.cpu_percent(interval=1)` | 后台 CPU 占用高会干扰本轮运行 | 必采 |
| `cpu_percent_after` | 运行后 CPU 占用 | `psutil.cpu_percent(interval=0)` 或短间隔采样 | 用于判断运行后系统是否仍处于高负载状态 | 建议采 |
| `ram_available_before_gb` | 运行前可用内存 | `psutil.virtual_memory()` | 低内存可能导致分页或 allocator 行为变化 | 必采 |
| `ram_available_after_gb` | 运行后可用内存 | `psutil.virtual_memory()` | 用于发现内存泄漏、大量缓存或未释放资源 | 建议采 |
| `exit_code` | 程序退出码 | subprocess 返回值 | 非 0 说明运行失败，该轮时间不能作为正常标签 | 必采 |
| `timeout` | 是否超时 | pipeline timeout 判断 | 超时样本不能和正常运行时间混用 | 必采 |
| `success` | 本轮是否成功 | `exit_code==0` 且未超时 | 用于过滤失败样本 | 必采 |

## 9. GPU/CUDA/OpenCL 预留环境指标

你现在主要跑 Windows + Rodinia OpenMP，这组字段可以暂时不采。但如果后续换到 CUDA/OpenCL 环境，必须补上。

| 指标字段 | 适用对象 | 采集方式 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|---|
| `gpu_name` | CUDA/OpenCL | `nvidia-smi` 或 OpenCL device query | GPU 型号决定核心数、频率、显存带宽 | GPU 必采 |
| `gpu_driver_version` | CUDA/OpenCL | `nvidia-smi` 或驱动 API | 驱动版本会影响 kernel launch、编译和运行时行为 | GPU 必采 |
| `cuda_toolkit_version` | CUDA | `nvcc --version` | 编译器和 runtime 版本会影响优化和兼容性 | CUDA 必采 |
| `cuda_runtime_version` | CUDA | runtime query | runtime 版本影响 API 行为和库实现 | CUDA 建议采 |
| `opencl_platform` | OpenCL | OpenCL query | 不同平台实现性能差异大 | OpenCL 必采 |
| `opencl_device` | OpenCL | OpenCL query | CPU/GPU/集成显卡设备差异非常大 | OpenCL 必采 |
| `global_work_size` | OpenCL | 运行参数 | 决定总并行工作项数量 | OpenCL 必采 |
| `local_work_size` | OpenCL | 运行参数 | 类似 CUDA block size，影响占用率和同步 | OpenCL 必采 |
| `grid_dim` | CUDA | kernel launch 参数 | 决定 block 网格规模 | CUDA 必采 |
| `block_dim` | CUDA | kernel launch 参数 | 决定每个 block 线程数，影响 occupancy 和访存合并 | CUDA 必采 |

## 10. 最小可行运行环境指标集

如果先做第一版 Windows + Rodinia OpenMP 实验，建议至少采集以下字段。

| 类别 | 最小必采字段 |
|---|---|
| 环境标识 | `env_id`, `timestamp`, `dataset_root`, `working_directory` |
| OS | `os_name`, `os_version`, `system_arch` |
| CPU | `cpu_model`, `cpu_physical_cores`, `cpu_logical_cores` |
| 内存 | `ram_total_gb`, `ram_available_gb` |
| 电源/负载 | `power_plan`, `cpu_percent_before`, `ram_available_before_gb` |
| OpenMP | `parallel_model`, `omp_num_threads`, `omp_schedule`, `omp_dynamic` |
| 单轮运行 | `run_id`, `program_id`, `input_id`, `run_index`, `runtime_sec`, `exit_code`, `timeout`, `success` |

## 11. 推荐采集方式

Windows 上建议组合使用 Python 和 PowerShell：

| 采集对象 | 推荐方式 |
|---|---|
| OS/CPU/内存 | Python `platform` + `psutil` |
| CPU 型号 | PowerShell `Get-CimInstance Win32_Processor` |
| Windows 版本 | PowerShell `Get-CimInstance Win32_OperatingSystem` |
| 电源计划 | PowerShell `powercfg /GETACTIVESCHEME` |
| OpenMP 参数 | 读取环境变量 `OMP_NUM_THREADS`, `OMP_SCHEDULE`, `OMP_DYNAMIC` |
| 每轮运行时间 | Python `time.perf_counter()` |

实验前建议明确设置：

```powershell
$env:OMP_NUM_THREADS = "4"
$env:OMP_SCHEDULE = "static"
$env:OMP_DYNAMIC = "false"
```

然后把这些环境变量写入环境表。不要依赖系统默认线程数，否则不同机器或不同 shell 下结果可能不一致。

## 12. 使用这些指标时的注意点

运行环境指标的主要作用不是解释程序算法复杂度，而是控制外部变量。建模时可以有两种做法：

| 做法 | 说明 |
|---|---|
| 固定环境，只作为元数据 | 第一阶段推荐。比如固定同一台 Windows 机器、同一电源模式、同一 OpenMP 线程数，只用环境字段保证可复现 |
| 多环境建模，把环境作为输入特征 | 后续扩展。比如同一程序分别在 1/2/4/8 线程下运行，让模型学习线程数和硬件资源对时间的影响 |

无论采用哪种方式，都不要把不同环境下的运行时间直接混成同一类标签。执行时间应理解为：

```text
runtime = program_static_features + input_scale + compile_config + run_environment + runtime_noise
```

其中运行环境就是 `run_environment`，必须被记录、控制或显式建模。
