# 问题3：实验环境规范化与运行时间采集规范

## 1. 基本原则

运行时间不是程序本身的唯一属性，而是“程序 + 输入 + 编译器 + 运行环境 + 运行参数”的联合结果。因此每条运行时间样本必须绑定一个 `env_id` 和一个 `input_id`。不要只保存 `program,runtime`，否则后续无法解释模型误差。

建议采用两层目标：

| 目标 | 规范 |
|---|---|
| 可重复 | 固定 OS、编译器、优化等级、输入、线程数；记录完整环境元数据 |
| 可泛化 | 设计多个环境 profile，而不是只在一台机器上采一套数据 |

## 2. 推荐实验环境矩阵

如果在自己的电脑上新建虚拟机，建议至少设置 3 个 CPU-only profile。CUDA/GPU 程序不要默认放进普通虚拟机，除非能稳定 GPU passthrough；否则应使用宿主机原生 Linux、WSL2 GPU、或单独 GPU 服务器。

| `env_id` | 用途 | vCPU | 内存 | 磁盘 | 适用数据集 | 说明 |
|---|---:|---:|---:|---:|---|---|
| `cpu_vm_small` | 小内存/低资源环境 | 2 | 4 GB | 60 GB SSD | PolyBench、小型 Rodinia | 用于观察内存压力和低并行度 |
| `cpu_vm_baseline` | 主基准环境 | 4 | 8 GB | 80 GB SSD | PolyBench、Rodinia OpenMP/CPU | 第一版模型的主环境 |
| `cpu_vm_memrich` | 内存充足对照 | 4 | 16 GB | 80 GB SSD | 内存密集程序 | 与 baseline 对比内存容量影响 |
| `cpu_vm_cpuscale` | CPU 核数扩展 | 8 | 16 GB | 100 GB SSD | OpenMP/Rodinia | 用于研究线程数和并行扩展 |
| `gpu_native_baseline` | GPU/CUDA 主环境 | 宿主机固定 | 宿主机固定 | SSD | Rodinia CUDA、CUDA Samples | 记录 GPU 型号、驱动、CUDA 版本；普通 VM 不推荐 |

虚拟机设置建议：

| 项目 | 规范答案 |
|---|---|
| OS | Ubuntu 22.04 LTS 或 24.04 LTS，固定一个版本作为主环境 |
| 编译器 | LLVM/Clang 18+，GCC 作为对照；记录完整 `clang --version` |
| CPU 分配 | vCPU 固定，不要运行时动态调整；尽量关闭 CPU overcommit |
| 内存 | 固定容量，关闭 ballooning/动态内存 |
| 磁盘 | 使用 SSD，数据集和输出目录放同一虚拟磁盘 |
| 电源策略 | 宿主机接电源，使用高性能模式；Linux 内可设 performance governor |
| 后台干扰 | 关闭无关服务、自动更新、杀毒全盘扫描、云同步 |
| 快照 | 采集期间不要频繁恢复快照；恢复后重新 warmup |
| 时间源 | 使用单调时钟，如 Python `time.perf_counter()` 或 C/C++ `clock_gettime(CLOCK_MONOTONIC)` |

## 3. 编译规范

同一个程序至少保留一种主编译配置，建议先以 `-O2` 作为主配置，因为参考文档中的 PrETi 路线也强调用优化后的 LLVM IR 更接近真实执行行为。

| 配置 | 编译参数 | 用途 |
|---|---|---|
| `debug_static` | `-O0 -g` | 便于 AST/CFG/IR 调试，不作为主运行时间标签 |
| `release_O2` | `-O2` | 主运行时间采集配置 |
| `release_O3` | `-O3` | 可选对照，观察编译优化强度 |
| `native` | `-O2 -march=native` | 可选，必须单独标记，不能与通用 `-O2` 混合 |
| `openmp` | `-O2 -fopenmp` | OpenMP 程序必须记录线程数和调度策略 |
| `cuda` | 固定 `nvcc` 版本和 `-O` 参数 | GPU 程序必须记录 CUDA Toolkit、driver、GPU 型号 |

规范要求：

| 问题 | 规范答案 |
|---|---|
| AST/IR/CFG 用什么优化等级？ | 主数据使用与运行二进制一致的 `-O2` IR；另外可保留 `-O0` 表示用于源码结构对照 |
| 是否把编译时间算入运行时间？ | 不算。编译时间单独记录，运行时间只统计程序执行 |
| 是否包含输入文件读取时间？ | 第一阶段建议包含端到端程序运行时间；若 I/O 明显主导，应额外采 `kernel_only_runtime` |
| 是否记录编译失败？ | 记录 `build_success=false`、错误摘要、编译命令，不要静默跳过 |

## 4. 运行轮次与统计口径

运行时间采集建议采用：

| 阶段 | 轮次 | 说明 |
|---|---:|---|
| 预热 | 5 次 | 不计入最终标签，用于 JIT/动态链接/cache/页表预热 |
| 正式测量 | 30 次 | 默认规范，保存每一轮原始 runtime |
| 异常扩展 | 50 次 | 如果 `CV = std/mean > 5%`，扩展到 50 次并检查干扰 |
| 极短程序 | 批量重复到总时长 >= 1 秒 | 单次小于 10 ms 时，外层重复执行或程序内循环，避免计时器噪声 |

最终标签建议：

| 字段 | 规范 |
|---|---|
| `runtime_sec_median` | 主标签，优先用于训练，抗异常值 |
| `runtime_sec_mean` | 辅助标签 |
| `runtime_sec_std` | 稳定性指标 |
| `runtime_cv` | `std / mean`，超过 5% 标记为不稳定 |
| `runtime_min`, `runtime_max` | 用于排查异常 |
| `warmup_runs`, `measured_runs` | 必须记录 |

异常值处理：

| 情况 | 处理 |
|---|---|
| 某轮运行失败 | 记录失败轮次，不参与 median，但该 program/input/env 标记为 `has_failure=true` |
| 超时 | 设置统一 timeout，例如 10 分钟；记录 `timeout=true` |
| CV 过高 | 重新运行一次；若仍高，保留但打 `unstable=true` |
| 第一次明显慢 | 由 warmup 吸收，不计入正式测量 |

## 5. 输入规模规范

每个程序至少准备 3 个输入规模：`small`、`medium`、`large`。如果程序过短，`small` 只用于调试，不进入正式训练。

| 规模 | 目标运行时间 | 用途 |
|---|---:|---|
| `small` | 0.1s 到 1s | 快速验证，避免过短 |
| `medium` | 1s 到 10s | 主训练样本 |
| `large` | 10s 到 120s | 检验可扩展性和内存压力 |

不同任务的输入规模必须使用问题 2 中的字段记录，例如：

| 任务 | 必须记录 |
|---|---|
| 数据库查找/B+Tree | 数据库记录数、查询数、key 大小、命中率 |
| 图算法/BFS | 节点数、边数、平均度、起点 |
| 矩阵运算 | `M,N,K`、数据类型、block size |
| 图像处理 | 宽、高、通道、帧数、迭代次数 |
| 聚类 | 点数、维度、簇数、迭代次数 |
| CUDA kernel | grid/block 维度、shared memory、输入字节数 |

## 6. CPU-only 测量建议

Linux CPU 环境下建议使用：

```bash
perf stat -r 30 -e cycles,instructions,cache-references,cache-misses,branches,branch-misses,page-faults,context-switches ./program
```

如果没有权限使用 `perf`，至少保留 Python 或 shell harness 的 wall-clock runtime，同时记录系统负载和进程退出码。

CPU 程序运行规范：

| 项目 | 规范答案 |
|---|---|
| 线程数 | 串行程序固定 1；OpenMP 程序测试 `1,2,4,8`，但每个线程数是不同样本 |
| CPU 亲和性 | 能设置则使用 `taskset` 固定核心；Windows/VM 中至少确保后台负载低 |
| 频率 | 尽量固定 performance governor；无法固定则记录 CPU 频率策略 |
| 缓存状态 | 主实验使用 warm-cache；cold-cache 作为单独实验，不混入主标签 |
| 输出 | 程序输出重定向到文件或 `/dev/null`，但不能改变程序计算逻辑 |

## 7. GPU/CUDA 测量建议

CUDA 程序受 GPU 型号、驱动、CUDA Toolkit、时钟、功耗墙、温度影响很大。普通 VM 如果没有 GPU passthrough，不建议采 CUDA 运行时间。

GPU 环境必须记录：

| 字段 | 示例 |
|---|---|
| `gpu_model` | NVIDIA RTX/A100/T4 等 |
| `driver_version` | `nvidia-smi` |
| `cuda_version` | `nvcc --version` |
| `sm_count`, `global_mem`, `memory_bus_width` | `nvidia-smi` 或 CUDA query |
| `power_limit`, `temperature` | 运行前后记录 |
| `block_dim`, `grid_dim`, `shared_mem_bytes` | 每次 kernel 配置 |

GPU 计时规范：

| 问题 | 规范答案 |
|---|---|
| 用 CPU wall-clock 还是 CUDA event？ | 两者都可采；主标签建议端到端 wall-clock，另采 kernel-only CUDA event |
| 是否包含 host-device 拷贝？ | 主端到端包含；kernel-only 不包含，两者字段分开 |
| 是否使用 Nsight 指标？ | 可选，但若采 L1/L2 hit、DRAM throughput，应作为动态性能表，不作为静态推理必需输入 |

## 8. 文件与数据落盘规范

建议后续采集脚本输出三类表：

| 文件 | 粒度 | 内容 |
|---|---|---|
| `program_static_features.csv` | 每个 `program_id + compile_config` 一行 | AST/CFG/LLVM IR 静态指标 |
| `run_records.csv` | 每个 `run_id` 一行 | env、input、轮次、runtime、退出码 |
| `run_summary.csv` | 每个 `program_id + input_id + env_id + compile_config` 一行 | median/mean/std/CV 等汇总标签 |
| `environment_manifest.json` | 每个 `env_id` 一份 | OS、CPU、内存、编译器、GPU、工具版本 |
| `input_manifest.csv` | 每个 `input_id` 一行 | 输入文件路径和规模字段 |

强制字段：

| 字段 | 说明 |
|---|---|
| `program_id` | 使用相对路径生成，避免同名文件冲突 |
| `input_id` | 同一程序不同输入规模必须不同 |
| `env_id` | 同一程序在不同 VM/硬件下必须不同 |
| `compile_config_id` | `O2`, `O3`, `native`, `openmp` 等 |
| `run_id` | 唯一标识一次运行 |

## 9. 第一版可执行规范

如果现在就开始采集，建议按这个最小规范执行：

1. 在 `cpu_vm_baseline` 上安装 Ubuntu 22.04/24.04、LLVM 18+、GCC、Graphviz、Python、NetworkX。
2. 先只跑 PolyBenchC，编译配置固定 `clang -O2`。
3. 每个 benchmark 设置 `small/medium/large` 三个输入规模。
4. 每个输入规模 warmup 5 次，正式 30 次。
5. 保存每轮原始时间，主标签用 median。
6. 同步保存 AST、CFG、LLVM IR 指标和输入规模字段。
7. 当 PolyBenchC 流程稳定后，再加入 Rodinia OpenMP/CPU。
8. CUDA 程序单独建 `gpu_native_baseline` 环境，不和 CPU-only VM 数据混在同一环境标签下。
