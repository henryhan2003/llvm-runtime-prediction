# 问题2：AST、CFG、LLVM IR 等代码表示的指标采集表

## 1. 数据表总结构

建议最终形成“一次运行一行”的宽表，核心字段如下：

| 字段组 | 示例字段 |
|---|---|
| 程序标识 | `program_id`, `dataset`, `relative_path`, `language`, `task_type`, `parallel_model` |
| 输入规模 | `input_size_n`, `matrix_m`, `matrix_n`, `graph_nodes`, `graph_edges`, `image_width`, `image_height`, `iterations` |
| 编译环境 | `compiler`, `compiler_version`, `opt_level`, `target_triple`, `build_flags` |
| 运行环境 | `env_id`, `os`, `cpu_model`, `vcpus`, `ram_gb`, `gpu_model`, `threads`, `block_size` |
| AST 指标 | 函数、调用、循环、分支、数组/指针、表达式、常量等 |
| CFG 指标 | 基本块、边、圈复杂度、循环、分支拓扑、图深度等 |
| LLVM IR 指标 | 指令总数、load/store、算术、分支、phi、call、GEP、向量/原子等 |
| 动态/硬件指标 | 可选训练辅助：cycles、instructions、cache miss、branch miss、page fault |
| 标签 | `runtime_sec_median`, `runtime_sec_mean`, `runtime_sec_std`, `runtime_cv`, `timeout`, `success` |

## 2. AST 指标

AST 指标更接近源码语法和算法结构，适合捕捉“程序写法”和高层语义，例如函数调用、循环嵌套、分支结构、数组访问形态。

| 指标字段 | 采集对象 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|
| `ast_node_count` | AST 总节点数 | 程序规模的粗粒度代理，节点越多通常代码路径、表达式和声明越多 | 必采 |
| `function_count` | `FunctionDecl` | 函数数量增加可能带来 call overhead，也可能代表模块复杂度更高 | 必采 |
| `call_expr_count` | `CallExpr` | 调用越多，直接开销、库函数开销、不可内联风险越高 | 必采 |
| `recursive_call_flag` | 函数调用图 | 递归会引入栈开销和动态执行次数不确定性 | 建议采 |
| `for_count` | `ForStmt` | for 循环通常代表重复执行，是运行时间增长的核心来源 | 必采 |
| `while_count` | `WhileStmt` | while 循环次数常依赖数据，运行时间方差可能更大 | 必采 |
| `do_while_count` | `DoStmt` | 与 while 类似，但至少执行一次 | 建议采 |
| `max_loop_depth` | 循环嵌套深度 | 嵌套越深，时间复杂度通常越高，如 `O(N^2)`、`O(N^3)` | 必采 |
| `loop_count_total` | for/while/do 合计 | 反映循环密度和潜在重复计算 | 必采 |
| `if_count` | `IfStmt` | 分支越多，控制流越复杂，可能增加 branch miss | 必采 |
| `switch_count` | `SwitchStmt` | 多路分支可能造成控制流复杂和跳转开销 | 必采 |
| `conditional_operator_count` | 三目运算 | 可能映射为 branch 或 select，影响控制流/数据流 | 可选 |
| `binary_operator_count` | `BinaryOperator` | 算术/比较/逻辑操作数量越多，计算需求越高 | 必采 |
| `arithmetic_operator_count` | `+,-,*,/,%,+=` 等 | 直接代理 CPU/FPU 计算量，乘除通常比加减更贵 | 必采 |
| `comparison_operator_count` | `<,>,==,!=` 等 | 比较通常伴随分支或循环条件，影响控制流 | 建议采 |
| `array_subscript_count` | `ArraySubscriptExpr` | 数组访问越多，内存流量越大，cache 行为更重要 | 必采 |
| `pointer_deref_count` | 指针解引用 | 指针访问可能带来别名和不规则访存，影响优化和缓存 | 建议采 |
| `malloc_free_count` | 动态内存 API 调用 | 动态分配增加运行时开销，也影响内存局部性 | 建议采 |
| `integer_literal_count` | 整数字面量 | 可用于识别固定循环边界、数组大小和常量规模 | 已有，必采 |
| `max_integer_literal` | 最大整数字面量 | 可能对应输入规模、数组维度或循环次数 | 已有，必采 |
| `avg_integer_literal` | 整数字面量均值 | 辅助区分小常量控制逻辑和大规模固定循环 | 已有，建议采 |
| `float_literal_count` | 浮点字面量 | 浮点公式/数值计算强度的辅助指标 | 可选 |
| `pragma_omp_count` | OpenMP pragma | 并行区域、线程调度和同步开销的重要来源 | OpenMP 必采 |
| `cuda_kernel_decl_count` | `__global__` kernel | CUDA 程序的 kernel 数量会影响 launch overhead 和并行粒度 | CUDA 必采 |

## 3. CFG 指标

CFG 指标反映控制流结构，适合解释分支、循环、基本块跳转和路径复杂度。

| 指标字段 | 采集对象 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|
| `cfg_function_count` | CFG 中函数图数量 | 函数越多，控制流图越分散，调用开销/内联影响更明显 | 必采 |
| `basic_block_count` | 基本块数量 | 基本块越多，控制流路径越复杂，指令缓存和跳转成本可能增加 | 必采 |
| `cfg_edge_count` | CFG 边数量 | 边越多，跳转关系越复杂，路径选择更多 | 必采 |
| `cyclomatic_complexity` | `E - N + 2P` | 圈复杂度越高，独立路径越多，分支预测和测试覆盖难度越高 | 必采 |
| `branch_block_count` | 出度大于 1 的基本块 | 分支块越多，branch miss 风险越高 | 必采 |
| `merge_block_count` | 入度大于 1 的基本块 | 合流点越多，phi/select 可能更多，数据依赖更复杂 | 建议采 |
| `avg_in_degree` | 平均入度 | 图连通复杂度指标 | 建议采 |
| `avg_out_degree` | 平均出度 | 分支发散程度指标 | 建议采 |
| `max_out_degree` | 最大出度 | switch 或多路跳转会增加跳转预测难度 | 建议采 |
| `loop_backedge_count` | 回边数量 | 回边越多，循环结构越复杂，重复执行成本越高 | 必采 |
| `natural_loop_count` | 自然循环数量 | 与程序热区数量相关 | 必采 |
| `max_cfg_loop_depth` | CFG 循环嵌套 | 比 AST loop depth 更贴近优化后控制流 | 必采 |
| `scc_count` | 强连通分量数量 | 可识别循环/递归控制结构 | 可选 |
| `cfg_depth` | 从入口到最深节点距离 | 近似最长控制路径，路径越长潜在执行步骤越多 | 建议采 |
| `unreachable_block_count` | 不可达基本块 | 可能来自编译/宏/死代码，影响静态规模但不影响动态时间 | 可选 |
| `critical_edge_count` | critical edge | 对插桩和优化敏感，可能影响后续 pass | 可选 |

## 4. LLVM IR 指标

LLVM IR 指标更接近机器执行前的中间语义，是预测资源需求的主力特征。当前三条正式流水线共用 `scripts/pipeline_new.py` 中的 IR 指标提取规则，采集范围如下表。

| 指标字段 | 采集对象 | 理论上如何影响执行时间 | 优先级 |
|---|---|---|---|
| `ir_instruction_count` | 非注释 IR 指令总数 | 静态指令规模越大，潜在执行成本越高，但需结合动态执行次数 | 必采 |
| `ir_line_count` | IR 行数 | 当前已有，粗略代码规模代理 | 已有，必采 |
| `load_count` | `load` | load 越多，内存读压力越高，cache miss 风险越高 | 已有，必采 |
| `store_count` | `store` | store 越多，内存写压力越高，写回/cache 一致性成本越高 | 已有，必采 |
| `memory_inst_count` | load/store/memcpy/memset/alloca/GEP 合计 | 内存需求总量代理 | 必采 |
| `getelementptr_count` | `getelementptr` | 地址计算和数组/结构体访问复杂度代理 | 必采 |
| `alloca_count` | `alloca` | 栈上对象数量，可能影响栈访问和优化机会 | 建议采 |
| `memcpy_count` | `llvm.memcpy` | 大块内存复制可能直接主导运行时间 | 建议采 |
| `memset_count` | `llvm.memset` | 初始化开销，尤其大数组初始化明显 | 建议采 |
| `call_count_ir` | `call` | 函数/库调用开销，不可见内部成本需要单独处理 | 已有，必采 |
| `external_call_count` | 外部函数调用 | 如 `malloc`, `printf`, BLAS/cuBLAS 调用可能主导时间 | 建议采 |
| `branch_count` | `br` | 控制跳转数量，和 CFG 分支复杂度对应 | 已有，必采 |
| `switch_count_ir` | `switch` | 多路分支，可能带来跳表/比较链 | 建议采 |
| `phi_count` | `phi` | SSA 合流和循环变量代理，常与循环/分支复杂度相关 | 已有，必采 |
| `select_count` | `select` | 分支消除或条件赋值，可能减少 branch 但增加数据依赖 | 可选 |
| `icmp_count` | `icmp` | 整数比较，常用于循环条件和分支条件 | 建议采 |
| `fcmp_count` | `fcmp` | 浮点比较，常用于数值算法条件判断 | 可选 |
| `add_count`, `sub_count` | 整数加减 | 基础算术开销，通常较低但执行次数多时重要 | 已有，必采 |
| `mul_count` | 整数乘法 | 计算需求高于加减 | 已有，必采 |
| `div_count`, `rem_count` | 除法/取余 | 高延迟指令，对运行时间影响可能显著 | 已有，必采 |
| `fadd_count`, `fsub_count` | 浮点加减 | 浮点计算密集任务的重要指标 | 必采 |
| `fmul_count` | 浮点乘法 | 矩阵/仿真类程序的重要指标 | 必采 |
| `fdiv_count` | 浮点除法 | 高延迟，通常比 fadd/fmul 更影响时间 | 必采 |
| `vector_inst_count` | `<N x type>` 向量操作 | SIMD/vectorization 程度，可能显著降低运行时间 | 建议采 |
| `atomic_count` | `atomicrmw`, `cmpxchg` | 并行同步热点，影响扩展性 | 并行程序必采 |
| `barrier_or_sync_count` | CUDA/OpenCL/OpenMP 同步相关调用 | 同步越多，并行等待成本越高 | 并行程序必采 |
| `constant_count_ir` | IR 中常量数量 | 当前已有，可辅助识别固定规模和循环边界 | 已有，建议采 |
| `max_constant_ir` | 最大常量 | 当前已有，可能对应数组规模/循环上界 | 已有，建议采 |
| `avg_constant_ir` | 常量均值 | 当前已有，辅助规模判断 | 已有，建议采 |
| `load_store_ratio` | `load_count / max(store_count,1)` | 区分读主导和写主导程序 | 派生，建议采 |
| `memory_arithmetic_ratio` | memory 指令 / arithmetic 指令 | 判断内存密集或计算密集的核心静态代理 | 派生，必采 |
| `branch_instruction_ratio` | control 指令 / 总指令 | 判断控制流复杂度和分支开销 | 派生，必采 |

## 5. 动态 profiling 指标

参考文档中提到 PrETi 的执行流、数据缓存和分支仿真，以及 Mapo 的动态性能模态。建议把动态指标分为“训练辅助可用”和“推理时不可依赖”两类：训练时可采集，最终模型可以做两种版本，一种只用静态表示，一种用静态 + 动态。

| 指标字段 | 采集方式 | 理论作用 |
|---|---|---|
| `bb_exec_count_*` | LLVM 插桩或 profiler | 静态基本块只有规模，动态执行次数能说明热路径 |
| `dynamic_instruction_count` | 插桩或 `perf stat` | 比静态 IR 指令数更接近真实执行量 |
| `cycles` | `perf stat` | CPU 时间直接硬件代理 |
| `instructions` | `perf stat` | 动态指令数，用于 IPC |
| `ipc` | `instructions / cycles` | 低 IPC 可能说明内存等待、分支错预测或同步等待 |
| `cache_references` | `perf stat` | cache 活跃程度 |
| `cache_misses` | `perf stat` | cache miss 越多，运行时间越可能受内存层次影响 |
| `branch_instructions` | `perf stat` | 动态分支数量 |
| `branch_misses` | `perf stat` | branch miss 会产生 pipeline flush，影响时间 |
| `page_faults` | OS/perf | 内存页错误会造成显著噪声或 I/O 影响 |
| `context_switches` | OS/perf | 系统调度干扰指标 |
| `gpu_l1_hit_rate`, `gpu_l2_hit_rate` | Nsight Compute/CUPTI | GPU 访存模型核心标签 |
| `gpu_dram_throughput` | Nsight Compute/CUPTI | GPU 内存带宽压力 |
| `gpu_occupancy` | Nsight Compute/CUPTI | 并行资源利用率 |

## 6. 输入空间规模指标

问题 1 中的任务类型必须记录输入规模，否则模型会把同一程序不同输入误认为同一特征，导致运行时间标签混乱。

| 任务类型 | 必采输入规模字段 | 说明 |
|---|---|---|
| 矩阵乘/线性代数 | `matrix_m`, `matrix_n`, `matrix_k`, `leading_dim`, `block_size` | GEMM/2mm/3mm/cholesky/lu 等都应记录矩阵维度 |
| 矩阵向量/向量操作 | `vector_n`, `matrix_m`, `matrix_n` | mvt、atax、bicg 等对内存带宽敏感 |
| stencil/网格迭代 | `grid_x`, `grid_y`, `grid_z`, `time_steps`, `stencil_radius` | hotspot、jacobi、fdtd、heat-3d、srad |
| 图算法 | `graph_nodes`, `graph_edges`, `avg_degree`, `max_degree`, `source_count` | BFS 等强依赖图结构，不只是节点数 |
| 数据库/树查找 | `record_count`, `query_count`, `key_size`, `tree_order`, `hit_rate` | b+tree 查询必须记录数据库大小和查询规模 |
| 排序 | `num_elements`, `key_width`, `value_width`, `distribution_type` | 随机、有序、重复键会影响分支和访存 |
| 聚类 | `num_points`, `num_dimensions`, `num_clusters`, `iterations`, `chunk_size` | kmeans/streamcluster |
| 图像处理 | `image_width`, `image_height`, `channels`, `frames`, `kernel_size`, `iterations` | deriche、heartwall、leukocyte、srad |
| 视频/帧处理 | `frames`, `frame_width`, `frame_height`, `tracked_points` | heartwall 等需要帧数 |
| 序列比对/生物信息 | `seq_len_a`, `seq_len_b`, `read_count`, `read_length`, `alphabet_size` | nw、nussinov、mummergpu |
| 分子/粒子仿真 | `particle_count`, `box_count`, `neighbors_per_particle`, `time_steps` | lavaMD、particlefilter |
| 压缩/编码 | `input_bytes`, `symbol_count`, `entropy_estimate`, `block_size` | huffman 的数据分布会影响分支和码长 |
| CUDA kernel | `grid_dim_x/y/z`, `block_dim_x/y/z`, `shared_mem_bytes`, `registers_per_thread`, `input_bytes` | GPU 运行时间强依赖 launch 配置 |
| OpenMP 程序 | `omp_threads`, `schedule`, `chunk_size`, `nested_parallel` | 线程数和调度策略必须进入样本 |

## 7. 最小可行指标集

如果先做第一版模型，建议先固定以下最小集：

| 表示 | 最小必采指标 |
|---|---|
| AST | `function_count`, `call_expr_count`, `for_count`, `while_count`, `if_count`, `switch_count`, `binary_operator_count`, `array_subscript_count`, `max_loop_depth`, `ast_node_count` |
| CFG | `basic_block_count`, `cfg_edge_count`, `cyclomatic_complexity`, `branch_block_count`, `natural_loop_count`, `max_cfg_loop_depth`, `cfg_depth` |
| LLVM IR | `ir_instruction_count`, `load_count`, `store_count`, `call_count_ir`, `branch_count`, `phi_count`, `getelementptr_count`, `add/sub/mul/div`, `fadd/fsub/fmul/fdiv`, `memory_arithmetic_ratio`, `branch_instruction_ratio` |
| 输入规模 | 按任务类型采集至少 2 到 5 个规模字段 |
| 标签 | `runtime_sec_median`, `runtime_sec_mean`, `runtime_sec_std`, `runtime_cv` |
