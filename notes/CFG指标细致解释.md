# CFG 指标细致解释

本文解释当前流水线中 CFG 指标的含义、它们在程序中对应什么、在 CFG 文件中通常怎样表现，以及理论上为什么会影响执行时间。

CFG 是 Control Flow Graph，即控制流图。它把程序按“基本块”和“跳转边”表示出来。基本块是连续执行的一段语句，中间没有跳转入口或跳转出口；边表示程序可能从一个基本块跳到另一个基本块。

例如源码：

```c
if (x > 0) {
    y = 1;
} else {
    y = 2;
}
return y;
```

它的 CFG 中通常会有一个判断块、两个分支块和一个汇合块。当前项目优先使用 LLVM `opt -passes=dot-cfg` 生成 `.dot` CFG；如果本机没有 `opt`，就使用 Clang `debug.DumpCFG` 的文本 fallback。fallback 中基本块通常表现为：

```text
[B3]
  if (x > 0)
  Succs (2): B2 B1

[B2]
  y = 1
  Succs (1): B0

[B1]
  y = 2
  Succs (1): B0
```

当前脚本对 CFG 的分析是轻量级图解析。它能统计基本块、边、分支、合流和近似回边，但没有做完整编译器级别的 dominator tree、natural loop 和 SCC 分析。因此部分字段是近似值，需要按下面说明理解。

## `cfg_function_count`

`cfg_function_count` 表示成功解析出的函数级 CFG 数量。

程序中每个有函数体的函数通常可以形成一张 CFG。比如 `main`、`kernel_gemm`、`init_array` 都可能各自对应一张函数控制流图。

理论影响执行时间的方式：函数 CFG 数量越多，程序控制结构越分散，潜在函数调用关系越复杂。不过它不表示所有函数都会执行，也不表示每个函数执行次数一样。对 benchmark 来说，真正重要的是包含核心循环的函数 CFG，而不是初始化或输出函数。

## `basic_block_count`

`basic_block_count` 统计 CFG 中基本块数量。

基本块可以理解为“一口气顺序执行的一段代码”。例如一个循环条件判断、一个循环体、一个 if 的 then 分支、一个 else 分支、一个 return 块，都可能是基本块。

在 Clang CFG 文本中，基本块通常表现为：

```text
[B4]
[B3]
[B2]
```

在 LLVM dot CFG 中，基本块通常表现为图节点，例如 `Node0x...`。

理论影响执行时间的方式：基本块越多，说明控制流被切得越碎，分支、循环、异常路径或复杂条件越多。基本块数量增加可能带来更多跳转、更复杂的路径选择和更差的指令局部性。但如果很多块属于错误处理或冷路径，动态执行时间不一定增加。

## `cfg_edge_count`

`cfg_edge_count` 统计 CFG 中控制流边的数量。

边表示程序可能从一个基本块跳到另一个基本块。在 Clang CFG 中通常来自：

```text
Succs (2): B2 B1
```

这表示当前块有两条后继边，分别到 `B2` 和 `B1`。

理论影响执行时间的方式：边越多，控制流选择越多。大量边通常来自 if、switch、循环、短路逻辑等结构。边多会增加路径复杂度，也可能增加分支预测压力。对运行时间建模而言，边数能补充 AST 中分支语句数量的信息。

## `cyclomatic_complexity`

`cyclomatic_complexity` 是圈复杂度。当前脚本使用近似公式：

```text
E - N + 2
```

其中 `E` 是边数，`N` 是基本块数。严格地说，多函数图应使用 `E - N + 2P`，`P` 是连通分量或函数图数量。当前实现是轻量近似。

理论含义是独立控制路径数量的近似。复杂度越高，说明程序中可选择路径越多，分支和循环结构越复杂。

理论影响执行时间的方式：圈复杂度高的程序可能有更多路径、更多条件判断和更复杂的分支预测行为。它还可能导致运行时间对输入数据更敏感。但圈复杂度不是“执行步数”，一个高圈复杂度的状态机可能每次只走很短路径，一个低圈复杂度的三重循环却可能运行很久。

## `branch_block_count`

`branch_block_count` 统计出度大于 1 的基本块数量。

出度大于 1 表示这个基本块有多个后继，通常对应 `if`、`switch`、循环条件或短路逻辑。例如：

```text
Succs (2): B2 B1
```

这样的块会被计为 branch block。

理论影响执行时间的方式：分支块越多，运行时需要做路径选择的地方越多。分支条件如果规律性强，CPU 可以较好预测；如果依赖随机数据或复杂输入，branch miss 会增多，流水线清空成本会增加。在 GPU 上，多分支还可能引起线程分歧。

## `merge_block_count`

`merge_block_count` 统计入度大于 1 的基本块数量。

入度大于 1 表示多个路径会汇合到同一个块。比如 if/else 后面的共同代码块就是 merge block。

理论影响执行时间的方式：合流块本身不一定慢，但它表示前面存在路径分裂。LLVM IR 中合流处常常会出现 `phi` 节点，用来选择不同路径带来的变量值。合流越多，数据依赖和控制依赖越复杂，编译器优化和预测分析也更困难。

## `avg_in_degree`

`avg_in_degree` 是基本块平均入度，即每个块平均有多少条边进入。

理论影响执行时间的方式：平均入度高说明控制流合流较多，路径交织更明显。它可以辅助判断程序是否有复杂的分支汇合结构。它通常不是单独强特征，更适合和 `merge_block_count`、`phi_count` 一起使用。

## `avg_out_degree`

`avg_out_degree` 是基本块平均出度，即每个块平均有多少条边出去。

理论影响执行时间的方式：平均出度高说明控制流发散程度高。顺序代码大多出度为 1；if、switch、循环条件会提高出度。出度越高，分支预测和路径选择的压力可能越大。

## `max_out_degree`

`max_out_degree` 是单个基本块的最大出度。

如果程序中有大型 `switch`，某个块可能有多个后继，`max_out_degree` 会比较高。

理论影响执行时间的方式：最大出度高说明存在多路控制选择。编译器可能生成跳转表，也可能生成比较链。跳转表对均匀分布输入可能较快，但对 cache 和间接跳转预测有影响；比较链则可能让不同 case 的路径长度不同。

## `loop_backedge_count`

`loop_backedge_count` 表示当前脚本识别到的回边数量。

回边可以粗略理解为“从后面的基本块跳回前面的基本块”的边，通常对应循环继续执行。例如循环体执行完后跳回循环条件判断。

当前实现使用块编号或节点编号的相对大小做近似：如果目标块编号小于或等于源块编号，就把它当作回边。这个方法简单，但不等价于严格的编译器 back edge，因为严格判断需要 dominator 分析。

理论影响执行时间的方式：回边是循环存在的重要信号。回边越多，程序可能有更多循环结构，动态执行次数可能远大于静态代码规模。对运行时间而言，循环回边通常比普通顺序边更重要。

## `natural_loop_count`

`natural_loop_count` 当前等于 `loop_backedge_count`。

严格意义上的自然循环是由 back edge 和 dominator 关系确定的一组基本块。当前项目还没有实现完整自然循环识别，所以这个字段是近似自然循环数量。

理论影响执行时间的方式：自然循环数量代表程序中可重复执行的控制区域数量。循环越多，热路径越可能集中在这些区域。后续如果要提高指标质量，应使用 LLVM loop analysis 或 NetworkX/dominator 算法重做这个字段。

## `max_cfg_loop_depth`

`max_cfg_loop_depth` 当前实现比较保守：只要识别到回边，就记为 1，否则为 0。

它目前不是严格的 CFG 循环嵌套深度。比如三重循环和单层循环在当前字段里可能都只是 1。真正的嵌套深度目前主要看 AST 指标 `max_loop_depth`。

理论影响执行时间的方式：如果未来实现为真实 CFG loop nesting depth，它会比 AST loop depth 更接近优化后控制流。优化后循环可能被展开、合并、删除或改变结构，因此 CFG 循环深度能补充源码层面的循环判断。

## `scc_count`

`scc_count` 表示强连通分量数量。强连通分量是图中一组可以互相到达的节点，通常能反映循环结构。

但当前脚本中这个字段暂时固定为 0，没有真正计算 SCC。

理论上，如果实现 SCC 统计，它可以帮助识别循环区域、递归式控制结构和复杂回路。SCC 越多或越大，说明控制流中可重复到达的区域越复杂，运行时间更可能受迭代次数影响。

## `cfg_depth`

`cfg_depth` 是当前脚本估算的 CFG 最大路径深度，即从入口或近似入口出发，沿边能走到的最深基本块距离。

它不是严格的最长执行路径，因为 CFG 中有循环；当前实现会避免重复访问已见节点，因此得到的是一个无重复节点的近似深度。

理论影响执行时间的方式：CFG 深度越大，说明从入口到某些路径可能经过更多阶段。它对分阶段算法、长 if/else 链、复杂初始化流程有一定解释力。但对循环密集程序，深度通常不如循环回边和输入规模重要，因为循环的动态重复次数不会直接体现在静态深度中。

## `unreachable_block_count`

`unreachable_block_count` 理论上表示不可达基本块数量，即从入口无法到达的代码块。

当前脚本中这个字段暂时固定为 0，没有做完整可达性分析。

理论影响执行时间的方式：不可达块不会影响实际运行时间，但会影响静态代码规模。如果不识别不可达代码，模型可能误以为程序更复杂。未来如果加入优化前后 CFG 对比，这个指标可以帮助区分死代码和真实热代码。

## `critical_edge_count`

`critical_edge_count` 统计 critical edge。当前脚本的判断规则是：一条边的源块出度大于 1，同时目标块入度大于 1，则认为是 critical edge。

这类边既从分支块出来，又进入合流块，中间没有单独基本块承接。编译器做插桩、SSA 修正或某些优化时，通常需要拆分 critical edge。

理论影响执行时间的方式：critical edge 本身不是运行时一定更慢的结构，但它表示控制流形状更复杂，也会影响编译器优化和插桩。对本项目来说，它更适合作为控制流复杂度和后续动态插桩难度指标。

## 使用 CFG 指标时的注意点

CFG 指标比 AST 更接近“程序会怎么走”，但它仍然是静态图。一个基本块是否执行、执行多少次，取决于输入数据和循环迭代次数。

对 PolyBench 这类规则循环程序，CFG 能很好识别循环和分支结构，但真正决定运行时间的仍是输入规模，例如 `N`、`M`、`TSTEPS`。对 Rodinia 这类更复杂 benchmark，CFG 分支、回边、critical edge 可能更能体现不规则控制流和数据依赖。

另外，当前项目在没有 LLVM `opt` 时使用 Clang DumpCFG fallback，因此 CFG 指标的精度低于完整 LLVM 图分析。后续如果要做严谨模型，建议安装 `opt` 并加入 PATH，或者在脚本中增加基于 LLVM pass 的 loop/dominator/SCC 指标。
